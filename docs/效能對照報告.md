# 效能對照報告：Go 版 vs Java 版推播服務

> **量測日期**：2026-07-31
> **受測對象**：同一份推播服務的兩個實作——
> Java 21 / Spring Boot 3.3.5（團隊 repo 的 `notification-service`，埠 8087）
> 與本專案的 Go 1.26 重寫版（埠 8088）。
> 兩者的對外行為由 [`test/contract/`](../test/contract/README.md) 的
> **14 個黑箱契約案例證明等價**（兩邊各 14/14 全綠），所以下面比的是
> 同一個功能的兩種實作，不是兩個不同的東西。

---

## 0. 先講結論

| 面向 | 結果 |
|---|---|
| **資源佔用** | Go 全面大幅領先：映像 **27×** 小、冷啟動 **16×** 快、閒置記憶體 **28×** 少 |
| **尾端延遲** | Go 領先且穩定：5000 條連線下握手 p99 **12.7ms vs 1131ms（89×）** |
| **典型延遲（吞吐）** | **兩者同一個數量級**，Go 略勝：扇出 p50 25.0ms vs 28.9ms（1.15×） |
| **暖機** | Java 冷容器第一批連線握手 p50 **873ms**，暖機後 1.41ms；**Go 沒有暖機效應** |
| **記憶體下限** | Go 在 **128MB** 撐得住 5000 條且零丟包；Java 在 128MB **起得來但不可用**，實用下限約 256MB |

**最重要的一句**：Go 版**不是「快一個數量級」**——在記憶體充足時，兩邊的扇出延遲差距只有 15%。
真正的差距在**每一條連線的成本**與**最壞情況的可預測性**，不在吞吐量。
把這件事寫清楚比端出漂亮的倍數重要。

## 1. 量測環境

| 項目 | 值 |
|---|---|
| CPU | AMD Ryzen 5 5600X（6 核 / 12 執行緒） |
| 記憶體 | 15.9 GiB |
| 作業系統 | Windows 11 Home 10.0.26200 |
| 容器執行環境 | Docker Desktop，Server 29.6.1，`linux/x86_64`，VM 12 vCPU / 7.7 GiB |
| 施壓工具 | 本專案的 [`test/load`](../test/load/README.md)（Go），**同一支程式、同一組參數壓兩邊** |
| Kafka | 各自獨立的單節點 KRaft（Go 用 `apache/kafka:4.1.0`，Java 用 `confluentinc/cp-kafka:7.6.1`） |

### ⚠️ 誠實聲明（請先讀完再引用任何數字）

1. **這是 co-located 壓測**：施壓端與被測服務在同一台機器、同一個 Docker VM 裡。
   施壓端自己要吃 CPU（5000 條時它有 5000 個 goroutine 在讀），這會**污染尾端延遲**。
   下面的數字**只能用於兩個實作之間的相對比較，不可當作對外可引用的容量上限**。
2. **每組只跑一次**（冷啟動那項跑了 3 次）。沒有重複取中位數，所以個位數百分比的差異不具意義。
3. **扇出延遲包含 Kafka 的傳輸與消費**，不是只有伺服器內部的扇出。刻意如此——
   那才是玩家實際等到的時間，而且兩邊測的是同一條路徑。
4. 兩邊的 Kafka 映像不同（沿用各自 compose 原本的設定）。這是變因，但它在
   「事件寫入 → 被消費」這一段對兩邊都存在，且遠小於觀察到的差異。
5. 百分位數用**最近排名法**（第 `ceil(p/100×N)` 個樣本），不插值。
   Prometheus 的 `histogram_quantile` 會插值，兩邊數字不該期待完全一致。

### 為什麼施壓端跑在容器網路裡，而不是從宿主

**第一次從宿主壓 5000 條時，3011 條在 dial 階段就被 reset**
（`An existing connection was forcibly closed by the remote host`），
而且**連壓測程式自己對 Kafka 的連線也一起被 reset**——那是另一個容器、另一個埠。

兩件事同時失敗，指向共同的上游：**Docker Desktop 的宿主埠轉發**，不是被測服務。
把施壓端改成 compose 網路內的一個 `alpine` 容器（掛載 Linux 版壓測執行檔）之後，
同樣 5000 條**全部連上、50000 則訊息一則不漏**。

順帶一提，網內施壓量到的握手 p50 是 **0.86ms**，經宿主轉發是 **8.35ms**——
差了近十倍，全是轉發層的成本。**在 Docker Desktop 上做壓測，別從宿主打。**

```bash
# 實際用的施壓方式
docker run --rm --network lucky-star-notify-go_default \
  -v "$PWD/bin:/host:ro" -e JWT_SECRET=... alpine:3.22 \
  /host/load-linux -target ws://notify-go:8088/ws -kafka kafka:9092 \
  -conns 5000 -rate 500 -rounds 10 -interval 1s -hold 40s
```

## 2. 映像大小

| | Go 版 | Java 版 | 比 |
|---|---:|---:|---:|
| `docker images`（未壓縮） | **18.6 MB** | 502 MB | **27.0×** |
| `docker image inspect .Size`（≈ pull 下載量） | **5.29 MB** | 146.1 MB | **27.6×** |

Go 版是 `scratch` + 單一靜態執行檔（`CGO_ENABLED=0`），連 shell 都沒有；
Java 版是 JRE 基底 + fat jar。這個差距與程式碼品質無關，是**執行模型的差別**：
Go 把執行期編進執行檔，Java 得帶一整個 JVM。

## 3. 冷啟動

`docker start` 到 `/actuator/health` 回 200 為止，從宿主緊迴圈輪詢（**不看 Docker 的
healthcheck**——那個是每 10 秒才探一次，量出來的會是探測間隔而不是啟動時間）。

| 次數 | Go 版 | Java 版 |
|---|---:|---:|
| 1 | 346 ms | 4791 ms |
| 2 | 301 ms | 4940 ms |
| 3 | 280 ms | 4140 ms |
| **中位數** | **301 ms** | **4791 ms** |

**約 16×**。Java 這 4~5 秒是 JVM 起動 + Spring context 掃描與組裝；
Go 是「執行檔載入 → 讀環境變數 → 開 listener」。

> 這個差距對**滾動更新**與**自動擴縮**是實際成本，不只是好看：
> 每次擴容都要等 5 秒才開始服務，跟等 0.3 秒，是兩種不同的營運手感。

## 4. 記憶體

### 4.1 閒置

兩邊都真的閒置（量測前先停掉 demo 的事件產生器，否則 Go 這側會多一份不對等的工作）。

| | Go 版 | Java 版 | 比 |
|---|---:|---:|---:|
| 閒置 RSS | **7.645 MiB** | 218.1 MiB | **28.5×** |
| 容器上限 | 128 MiB | 1.25 GiB | |
| 佔用率 | 5.97 % | 17.04 % | |

### 4.2 帶著連線

`docker stats --no-stream`，量在連線全部建立、保持 40 秒的中段。

| 連線數 | Go @128M | Java @1280m |
|---:|---:|---:|
| 0（閒置） | 7.6 MiB | 218.1 MiB |
| 100 | 25.0 MiB | 303.9 MiB |
| 1 000 | 48.9 MiB | 441.0 MiB |
| 5 000 | **123.7 MiB（96.6 %，貼上限）** | 969.6 MiB |

**每條連線的邊際成本**（用 5000 與 100 之間的差算）：
Go ≈ **20.6 KiB/條**、Java ≈ **139 KiB/條**，約 **6.7×**。

Go 這 20 KiB 大致是：gorilla 的讀寫緩衝各 4 KiB、兩條 goroutine 的堆疊、
outbound channel（64 格）與 session 結構。

### 4.3 ⚠️ JVM 的 RSS 是**高水位線**，不會回落

跑完 5000 條之後，把連線降回 100 條再量一次：

| | 100 條（跑過 5000 之前） | 100 條（跑過 5000 之後） |
|---|---:|---:|
| Java | 303.9 MiB | **1018 MiB** |
| Go（重啟後全新容器） | — | **11.0 MiB** |

Java 那個 1018 MiB 是**只掛著 100 條連線**時量到的。JVM 預設不把已 commit 的堆歸還作業系統，
所以「尖峰之後就一直維持在尖峰」。這件事在**共用主機或容器密度高**的環境下是真金白銀的成本。

## 5. 連線建立延遲（握手）

量的是 `dial` 到收到 STOMP `CONNECTED` 為止：TCP + WebSocket upgrade + STOMP 握手 + JWT 驗章。
也就是「玩家從按下連線到可以收訊息」的實際成本。建立速率固定 **500 條/秒**。

| 連線數 | 實作 | p50 | p95 | p99 | max |
|---:|---|---:|---:|---:|---:|
| 100 | Go @128M | **1.02 ms** | 13.87 ms | 21.75 ms | 23.67 ms |
| 100 | Java @1280m（暖機後） | 1.41 ms | 6.93 ms | 13.04 ms | 15.57 ms |
| 1 000 | Go @128M | **0.86 ms** | 6.64 ms | 30.55 ms | 44.81 ms |
| 1 000 | Java @1280m | 13.56 ms | 268.08 ms | **1073.97 ms** | 1103.74 ms |
| 5 000 | Go @128M | 1.26 ms | 11.82 ms | 38.93 ms | 118.05 ms |
| 5 000 | Go @1280m（同 Java 預算） | **0.94 ms** | **1.39 ms** | **12.70 ms** | 28.66 ms |
| 5 000 | Java @1280m | 1.78 ms | 204.66 ms | **1131.52 ms** | 3085.25 ms |

**在相同記憶體預算下，5000 條連線的握手 p99 是 12.70 ms vs 1131.52 ms——89×。**
p50 只差 1.9×，但 p99 差了兩個數量級：這正是「平均值是延遲的壞指標」的教科書案例。
Java 的尾端來自 GC 停頓與 Tomcat 執行緒池排隊；Go 這邊每條連線就是兩個 goroutine，
排程單位小得多，尾端因此平坦。

## 6. 扇出延遲

量的是**事件寫進 Kafka 前一刻**到 client 收到 `MESSAGE` 為止。
每輪一則 `rank.update`（body 含 3 筆排行資料），共 10 輪、每輪間隔 1 秒。

| 連線數 | 實作 | 收訊 | p50 | p95 | p99 | max |
|---:|---|---:|---:|---:|---:|---:|
| 100 | Go @128M | 1000/1000 | **2.52 ms** | 13.80 ms | 13.86 ms | 13.91 ms |
| 100 | Java @1280m（暖機後） | 1000/1000 | 3.91 ms | 21.27 ms | 21.45 ms | 21.58 ms |
| 1 000 | Go @128M | 10000/10000 | **6.37 ms** | **13.12 ms** | **14.93 ms** | 15.83 ms |
| 1 000 | Java @1280m | 10000/10000 | 12.16 ms | 34.12 ms | 35.54 ms | 37.13 ms |
| 5 000 | Go @128M | 50000/50000 | 118.46 ms | 552.44 ms | 748.49 ms | 813.54 ms |
| 5 000 | **Go @1280m（同 Java 預算）** | 50000/50000 | **25.05 ms** | **44.81 ms** | **52.23 ms** | 56.55 ms |
| 5 000 | Java @1280m | 50000/50000 | 28.91 ms | 68.46 ms | 75.05 ms | 132.05 ms |

**所有組合的收訊率都是 100.00%**，`notify_outbound_dropped_total` 沒有被觸發過——
背壓政策（滿了就驅逐）在這個量級下不需要作用。

### ⚠️ 那個 118 ms 是怎麼回事：GOMEMLIMIT 的代價

Go 在 5000 條、128 MB 上限時，扇出 p95 是 **552 ms**——比 Java 差 8 倍。
乍看像是實作輸了，但把記憶體預算放寬到與 Java 相同（1280m / `GOMEMLIMIT=1GiB`）
**其他什麼都沒改**，同一組壓測變成 p95 **44.81 ms**：

| Go @5000 條 | 記憶體 | 扇出 p50 | 扇出 p95 | 扇出 p99 |
|---|---:|---:|---:|---:|
| 128M / `GOMEMLIMIT=100MiB` | 123.7 MiB（96.6 %） | 118.46 ms | 552.44 ms | 748.49 ms |
| 1280m / `GOMEMLIMIT=1GiB` | 188.0 MiB（14.7 %） | **25.05 ms** | **44.81 ms** | **52.23 ms** |

成因是 **`GOMEMLIMIT` 是軟上限不是硬上限**：一旦用量逼近它，GC 就**持續**運行來把量壓回去，
CPU 被 GC 吃掉，延遲就漲上去。服務**不會死、不會丟訊息**（收訊仍是 100%），
但延遲會被 GC 吃掉一大塊——這是 Go 在記憶體受限時的典型行為，
與 Java 在同樣情況下直接 OOMKilled 是完全不同的失敗模式。

> **這是本次量測最有價值的一段**。原本的 128 MB 是 Phase 4 隨手訂的容器上限，
> 而它在 5000 條時已經是瓶頸。結論不是「Go 慢」，而是
> **「`GOMEMLIMIT` 要跟著預期的連線數一起訂」**——
> 大約每 1000 條連線抓 25 MiB，再留一倍餘裕給 GC。

## 7. Java 版的記憶體下限

計畫書要求「用**相同的 `mem_limit`** 測一次」。Java 版原本的設定是
`mem_limit: 1280m` + `-Xmx1g`，直接套 128 MB 上限只會馬上死，
所以改用 `-XX:MaxRAMPercentage=60`，讓 JVM 依容器上限自己配置——
這比我手挑一個 `-Xmx` 公允得多。

每一組都是**全新容器**，量的是冷啟動之後第一批 100 條連線。

| 容器上限 | 啟動 | RSS | 握手 p50 | 扇出 p50 / p95 | 收訊 | 判定 |
|---:|---|---:|---:|---:|---:|---|
| 128 m（`-Xmx64m` 手設） | 4.04 s 後**被 OOMKilled（137）** | — | — | — | — | ❌ 死 |
| 128 m（`MaxRAMPercentage=60`） | 4.72 s healthy | 128 MiB（**99.98 %**） | **12 278 ms** | 16.96 / **4 048 ms** | 1000/1000 | ⚠️ 活著但不可用 |
| 256 m | 3.79 s healthy | 217.4 MiB（84.9 %） | 206 ms | 16.67 / 42.02 ms | 1000/1000 | ✅ 可用 |
| 384 m | 4.33 s healthy | 215.8 MiB（56.2 %） | 207 ms | 6.65 / 63.59 ms | 1000/1000 | ✅ 可用 |

**Java 版的實用下限約 256 MB**，而且那時 RSS 已經佔掉 85%、幾乎沒有餘裕。
對照組是 **Go 版在 128 MB 撐住 5000 條連線且零丟包**。

128 MB 那一組值得單獨看一眼：它**沒有死**，健康檢查也過，但每條連線的握手要 **12.3 秒**。
外部監控只看 healthcheck 的話會顯示一切正常——這種「活著但沒在服務」的狀態，
比直接掛掉更難察覺。

## 8. JIT 暖機：Java 一次性、Go 沒有

| | 冷容器的第一批 100 條，握手 p50 | 暖機後 |
|---|---:|---:|
| Java @1280m | **873.45 ms** | 1.41 ms |
| Go @128M | **1.05 ms** | 1.02 ms |

Java 的第一批連線比暖機後慢 **620×**，之後就恢復正常——這是 JIT 編譯與類別載入的
一次性成本，不是缺陷。Go 冷熱兩個數字**在量測誤差內完全一樣**，因為它沒有 JIT，
執行的一直是同一份機器碼。

實務上的意義：**滾動更新剛換上去的那個 pod，前幾百個使用者的體感是不一樣的**。
Java 要靠預熱流量或延後加進負載平衡來遮蓋，Go 不需要這一步。

## 9. 這份報告**沒有**證明的事

避免過度推論，明列出來：

- ❌ **沒有證明 Go 語言比 Java 快。** 在記憶體充足時兩邊的扇出延遲差 15%，
  同一個數量級。這類服務的瓶頸是 I/O 與排程，不是語言的算術速度。
- ❌ **沒有測到任一邊的容量上限。** 5000 條是施壓端在這台機器上的舒適區，
  不是被測服務的極限；co-located 也讓「再往上壓」的數字不可信。
- ❌ **沒有測長時間穩定性。** 每組只跑一分鐘出頭，看不到記憶體洩漏、
  也看不到 Java 的 full GC 週期。
- ❌ **沒有測多副本。** 兩個實作都只能單副本（原因見
  [ADR-001](ADR-001-為什麼用-Go-重寫推播服務.md) 的「未來工作」），這不是本次的變因。
- ❌ **Spring 沒有被調校過。** 用的是團隊 repo 原本的設定。
  換 GC（ZGC/Shenandoah）、開 CDS、或改用 GraalVM native-image 都可能大幅改善
  啟動時間與尾端延遲——那會是另一份報告。

## 10. 怎麼重現

```bash
# 1. 起 Go 版
docker compose -f deploy/docker-compose.yml up --build -d --wait

# 2. 起 Java 版（團隊 repo，唯讀使用、不 commit）
cd <團隊 repo> && docker compose up -d notification-service

# 3. 建 Linux 版壓測執行檔
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o bin/load-linux ./test/load

# 4. 在容器網路裡施壓（**不要從宿主打**，見 §1）
docker run --rm --network lucky-star-notify-go_default \
  -v "$PWD/bin:/host:ro" -e JWT_SECRET=lucky-star-demo-secret-do-not-use-in-production \
  alpine:3.22 /host/load-linux \
  -target ws://notify-go:8088/ws -kafka kafka:9092 \
  -conns 5000 -rate 500 -rounds 10 -interval 1s -hold 40s -out /dev/null

# 5. 在 -hold 期間另開一個視窗量記憶體
docker stats --no-stream notify-go
```

Java 版把 `--network` 換成 `lucky_star_casino_lucky-network`、
`-target` 換成 `ws://notification-service:8087/ws`、
`-kafka` 換成 `lucky-star-kafka:29092`、`JWT_SECRET` 換成團隊 repo `.env` 裡那把。

全部原始樣本（每一則訊息的延遲）由 `-out` 寫成 JSON，留在 `test/load/results/`
（已被 gitignore——報告要進版控，幾百 KB 的原始檔不用）。
